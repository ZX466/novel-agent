- 现有事件类型(chat.py:278-321): start / start-step / text-start / text-delta* / text-end /
  perf / error / finish-step / finish, 结束哨兵 [DONE]; 统一编码 data: {json}\n\n。
- 计时已有: backend/app/pipeline/nodes.py:24 _timed 写 state["perf"]["{stage}_ms"]
  (retrieval / draft / refine / evaluate / safety)。
- perf 事件(chat.py:318) 在文本流结束后才发一次, payload 为扁平 ms 字典。
- 前端已能接收自定义事件: frontend/src/lib/perf-transport.ts 解析 perf → Chat.tsx:18 lastPerf

--- 2. 缺口 ---
- G1 无阶段开始/结束事件 → UI 只能等全部结束, 无法实时点亮阶段。
- G2 _timed 用 perf[f"{stage}_ms"] = ... 覆盖写; refine 多轮时只剩最后一轮耗时。
- G3 无失败归属: 节点抛错冒泡到 stream_pipeline → _event_stream 映射为通用 error, 前端不知哪个阶段失败。
- G4 task_type 路由(graph.py:84 _should_run_stage)会跳过阶段, 但无 skipped 语义 → UI 分不清"未开始/已跳过"。
- G5 流中断不可知: GeneratorExit 后服务端无法再发事件(只能后台落 Redis ai-draft:{novel_id});
  前端 reconnectToStream 返回 null, 无 resume; 前端只能靠"没有 finish"猜测。

--- 3. 事件协议 v1（新增 stage 事件, 复用现有通道）---
所有事件仍在同一条 SSE 流内, 由 type 区分; stage 是新增类型, 未知类型前端按 default 忽略 → 向后兼容。

事件类型: stage
字段:
  type        固定 "stage"
  seq         单调递增整数(每请求从 1 开始), 用于前端排序与丢包检测
  stage       retrieval | draft | refine | evaluate | safety
  status      started | succeeded | failed | skipped
  iteration   refine/evaluate 的轮次(0 起); 其余阶段恒为 0
  elapsed_ms  仅 succeeded/failed 有; 由 _timed 的实测值(保留 1 位小数)
  summary     仅 succeeded 有; 白名单统计字段, 见下
  code        仅 failed 有; 稳定机器码, 如 stage_error / timeout / llm_auth
  detail      仅 failed 有; 面向用户的安全文案(禁止堆栈/密钥/提示词)

payload 示例(每条独立 SSE 事件):
  data: {"type":"stage","seq":3,"stage":"retrieval","status":"started","iteration":0}
  data: {"type":"stage","seq":4,"stage":"retrieval","status":"succeeded","iteration":0,"elapsed_ms":412.3,"summary":{"hits":7,"chars":1840}}
  data: {"type":"stage","seq":9,"stage":"refine","status":"started","iteration":1}
  data: {"type":"stage","seq":10,"stage":"refine","status":"succeeded","iteration":1,"elapsed_ms":5120.0,"summary":{"chars":2310}}
  data: {"type":"stage","seq":11,"stage":"evaluate","status":"succeeded","iteration":1,"elapsed_ms":880.5,"summary":{"score":0.82,"dims":6,"fallback":false}}
  data: {"type":"stage","seq":12,"stage":"safety","status":"succeeded","elapsed_ms":3.1,"summary":{"matched_count":0,"max_severity":"none","should_block":false}}
  data: {"type":"stage","seq":13,"stage":"refine","status":"skipped","iteration":2,"reason":"task_type=continue"}

summary 白名单(逐阶段, 只允许这些键, 全部为数值/布尔/枚举, 不含自由文本):
  retrieval: hits(int) | chars(int) | source(structured|vector|none)
  draft:     chars(int)
  refine:    chars(int)
  evaluate:  score(float) | dims(int) | fallback(bool)
  safety:    matched_count(int) | max_severity(str) | should_block(bool)
  通用:      skipped 时用 reason 枚举(task_type|no_context|disabled)

阶段顺序与生命周期(与 graph.py 实际拓扑一致):
  generate:  retrieval → draft → refine* → evaluate* → (route) → safety
  continue/assistant: retrieval → draft → safety        (refine/evaluate 发 skipped)
  rewrite/polish:     retrieval → refine → safety        (draft/evaluate 发 skipped)
  outline:            retrieval → draft → safety
  extract:            draft                              (其余发 skipped)
  refine/evaluate 循环: 每轮各发一对 started/succeeded, iteration 递增;
  未达阈值且 iterations < pipeline_max_iters 时再次 refine(前端据此显示"第 N 轮精修")。

原有事件保持不变; 现有 perf 事件在协议 v2 建议扩展为包含逐轮数组, 但不阻塞 v1。

--- 4. 实现要点（供实施 Agent, 不改协议）---
- 事件产生点: 建议在 graph.py 的 on_token 同级再加一个 on_event 回调, 由 _timed 装饰器调用
  (started 在 t0 之前, succeeded/failed 在 finally), 避免逐个节点手写。
- 传递路径: run_pipeline/stream_pipeline 增加 on_event 参数 → _event_stream 把事件写进同一 token_queue
  (需把队列元素由 str 改为 (kind, payload) 或复用哨兵), 保证与 text-delta 的顺序稳定。
- seq 由 _event_stream 侧统一分配(单一写入点), 节点侧不自行编号, 避免并发/循环下乱序。
- summary 由节点返回值计算(如 len(retrieved_context)), 不在事件层读取 state 全文。
- 向后兼容: 未知 type 已由 perf-transport.ts 的 default 分支忽略; 前端改造属 Claude 域。

--- 5. 安全 / 合规 / 风险评估（codex 主责）---
[S1] 提示词与正文泄漏 — 中危, 必须约束
  summary 白名单只允许长度/计数/评分; 禁止把 topic、prompt、draft/refined 正文、feedback、
  retrieved_context 原文、provider_config 或 API Key 放进任何 stage 事件。
  实施验收: 单测断言事件 JSON 不包含 topic 明文与 sk- 前缀(复用 _redact_key)。
[S2] 内部错误细节泄漏 — 中危
  failed 事件的 detail 必须是面向用户的安全文案(复用现有 litellm 异常分支的措辞),
  code 为稳定枚举; 异常原文仅进 logger(已过 _redact_key)。
  禁止透传 str(exception) / 堆栈 / 上游响应体。
[S3] 存在性/租户探测面 — 低危
  stage 事件不得包含 novel_id、owner_key_hash、document_id; 现有 _guard_novel_owner 前置校验保持不动。
  建议只发阶段名与统计值, 不携带任何业务标识。
[S4] 计数侧信道 — 低危
  retrieval hits/chars 可被用于推断他人语料规模; 但该请求已通过 owner 校验, 且只能观测自有 novel,
  风险可接受; 若需更严可把 chars 改为量级桶(0/1-1k/1k-10k/10k+)。
[S5] 事件洪泛 / 放大 — 低危
  事件数上限: 每阶段每轮 2 条 + 固定事件, 受 pipeline_max_iters 约束;
  建议硬上限 64 条/请求, 超出后丢弃 stage 事件(不影响文本与 finish)。
[S6] 流中断可见性 — 中危, 协议层无法完全解决
  客户端断开后服务端不再能推送, 只能靠: (a) 前端检测"未收到 finish/[DONE]" → 判定中断;
  (b) 复用已有 Redis 落盘 ai-draft:{novel_id}(graph.py:350) 供前端恢复轮询。
  建议在协议文档中明确: 前端必须以 finish 事件作为"完成"的唯一判据, 超时未见 finish 视为中断。
[S7] 顺序/重放 — 低危
  seq 单调 + 单写入点可防乱序; 事件不含时间戳与随机数, 无重放价值; SSE 无鉴权变更。
[S8] 合规 — 无新增个人数据
  事件仅含统计与阶段名, 不新增持久化(仅日志与流内传输), 不改变数据保留策略。

结论: 协议 v1 可实施; 必须先落实 S1/S2 的白名单与安全文案约束, 并以单测固化(禁止明文泄漏)。
建议评审重点: (1) summary 白名单是否足够; (2) failed 事件 code/detail 的枚举表; (3) 64 条上限是否合理。
