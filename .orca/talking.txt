### 1. 表结构 `character_relationships`
| 列 | 类型 | 说明 |
|----|------|------|
| id | Integer PK autoincrement | |
| novel_id | Integer NN, index | 作品域 |
| subject_id | Integer NN, FK→characters.id | 起点角色 |
| object_id | Integer NN, FK→characters.id | 终点角色 |
| relation_type | String(64) NN | 关系名（师徒/恋人/宿敌…，free-form 免迁移） |
| description | Text NN default "" | 关系说明 |
| strength | Integer NN default 0 | 强度（0-10，图权重） |
| metadata_json | JSONB NN default {} | 预留扩展 |
| created_at / updated_at | tz timestamp | server_default now |

约束：
- `UniqueConstraint(novel_id, subject_id, object_id)` → 每个有向点对单条边，符合"拖连即改关系"
- `CheckConstraint(subject_id != object_id)` → 无自环
- 迁移：`down_revision=b7c8d9e0f1a2`，upgrade 建表+索引+FK+约束，downgrade drop 表，可回滚

### 2. API 端点（子路由，前缀 `/v1/documents/{doc_id}/characters/relationships`）
| 方法+路径 | 语义 |
|-----------|------|
| GET `/graph` | 一次取全：`{nodes:[{id,name,role}], edges:[{subject_id,object_id,relation_type,description,strength}]}`（前端渲染用） |
| PUT `/{subject_id}/{object_id}` | 单边 upsert（前端拖线改关系）：body relation_type/description/strength |
| DELETE `/{subject_id}/{object_id}` | 断开一条边（前端取消连线） |
| POST `/import` | 批量导入（大纲一键生成）：body `[{subject_name,object_name,relation_type,description,strength}]`，后端 name→id 解析，未知角色返回 404 |

统一 `load_parent` 校验 novel 存在且未删；subject/object 必须在同一 novel 内；服务层异步，错误按 integrity/not-found 转 409/404。

### 3. Schema 层（app/schemas/novel_memory.py 内新增，或新建 relationship.py）
`CharacterRelationshipBase`(subject_id,object_id,relation_type,description,strength)、`Upsert`、`Read`(+id+时间戳)、`GraphNode`、`GraphEdge`、`RelationshipGraph`、`ImportItem`/`ImportRequest`。

### 4. 前端图组件契约（供 Claude 前端域）
- GET `/graph` 一次返回 nodes+edges，前端可直接渲染力导向图
- 拖出新连线→`PUT /{sub}/{obj}`；拖动修改→`PUT`（upsert 覆盖）；删除连线→`DELETE`
- 单边字段精简，契合 Pi 提示"人物树≤10 角色、单行精简"

### 5. 预留轻量序列化（Pi 提示）
设计 `serialize_graph(novel_id) -> str`，渲染为单行紧凑文本（如 `A师徒B;A恋人C`）供后续章节提示词注入；暂不落地，仅预留 schema 可扩展性。

--- P1（必须改设计后再实施）---
[P1-1] 缺 ON DELETE 行为 → 删角色会 500，角色永远删不掉
  delete_character（app/services/character.py:146-149）是硬删（session.delete）。你的 FK 未声明 ondelete，
  默认 NO ACTION → 角色只要有关联边，DELETE /characters/{id} 抛 ForeignKeyViolation，端点未捕获 → 500。
  要求: subject_id/object_id 的 FK 全部 ondelete="CASCADE"；ORM 侧同步 passive_deletes=True（或 service 显式清理），
  迁移里写死 ondelete。验收: 新增测试「删除有关联边的角色 → 204 且其边全部消失」。
[P1-2] 跨作品完整性只靠应用层 → 必须 DB 兜底（R6-2 P1 同款教训）
  novel_id/subject_id/object_id 三者一致目前只靠 service 校验。并发或 import 批量路径一旦漏检，
  就会写出「A 作品的角色连到 B 作品的边」——跨租户数据泄漏面。
  要求: 照 plot_events 既有做法（app/models/plot_event.py:44-51 +
  alembic/versions/c0d1e2f3a4b50_enforce_same_novel_prev_event.py）用复合 FK：
    - characters 先加 UniqueConstraint(novel_id, id)（PG 要求被引用列唯一）
    - ForeignKeyConstraint(["novel_id","subject_id"], ["characters.novel_id","characters.id"])
    - ForeignKeyConstraint(["novel_id","object_id"], ["characters.novel_id","characters.id"])
  这样「同作品」由数据库保证，应用层校验降级为体验优化。
  验收: 测试「用 B 作品的角色 id 在 A 作品建边 → 409/404，且库里无边」。

[P1-3] GET /graph 的 N+1 与排序缺失 → 契约不完整
  设计只写「一次取全」，但未定实现与排序：若按边逐条查角色会 N+1。
  要求: 两条查询搞定（select 角色 where novel_id；select 边 where novel_id），
  在内存做 name→node 映射；nodes 按 name 升序（与 list_characters 的 order_by(Character.name) 一致）、
  edges 按 (subject_id, object_id) 稳定排序，保证前端渲染与快照可比。
  另: 端点返回里不要包含 novel_id（见 S3）。
--- P2（建议实施时一并处理）---
[P2-1] 唯一约束与「拖线即改」语义
  UniqueConstraint(novel_id, subject_id, object_id) 允许 A→B 与 B→A 同时存在（两条有向边）。
  如果产品语义是「一对角色只有一种关系」，应改 (novel_id, least, greatest) 的规范化无向约束或
  在服务层合并双向；请先与 Claude/前端确认拖拽语义，再定唯一键。
  PUT 建议用 pg_insert(...).on_conflict_do_update(constraint=...) 实现真 upsert（仓库已有先例：
  app/services/creative_kit.py:76 on_conflict_do_nothing），避免「先查再写」的并发竞态。

[P2-2] strength 约束与默认值
  strength 目前仅 default 0，无范围约束。请加 CheckConstraint("strength BETWEEN 0 AND 10")，
  Pydantic 侧 Field(ge=0, le=10)；relation_type 加 max_length=64 与 strip 归一化（空串 → 422），
  防止超长/空白关系名污染后续提示词注入（Pi 的轻量序列化路径直接吃这个字段）。

[P2-3] import 端点语义

  未知角色「整批 404」还是「跳过并回报」需明确定义；返回体给出 created/updated/skipped 计数，
  不要静默部分成功。name→id 解析必须限定 novel_id（get_character_by_name 已支持，app/services/character.py:90）。

[P2-4] 表名/字段命名与既有惯例
