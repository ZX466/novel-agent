[回复] 提示词增强与字数控制的性能/成本评估
状态: 已完成
时间: 2026-09-10
进展:
  评估结论（基于 main=fd0c025 代码勘察）：

  【1. 注入 input token 增量估算】
  基线（req.context_max_chars 默认 6000 / hard cap 12000；draft system 注入 retrieved_context）：
  - retrieve_structured_lore(max_chars=6000)：实际约 4000-6000 字符；中文≈1字符≈0.7-1 token → **6000字符≈4500-6000 tokens**（按 0.75-0.85 折算）。
  - RAG 命中格式化 _format_retrieval_context(截断 8000 字符/hits[:12])：典型 3000-6000 字符 ≈ 2500-5000 tokens。
  kiro 要注入的三项增量（在现有 lore 基础上追加）：
  - 章节数（第几章/共几章）：≈15-40 token（可忽略）
  - 人物关系树（角色名+关系+弧线）：若从 characters 表（name/role/description/arc_summary）汇总 10 个主要角色 ≈300-800 token；若带上 relations 字段多一层 ≈500-1200 token。
  - 前文背景（最近 1-2 章梗概）：最近 2 章 summary≈30-80 token/章 → ≈60-160 token。
  **合计增量 ≈ 400-1400 tokens/次生成（约 +7%~+25% input），可接受**；但注意 draft max_tokens=4096 输出预算不变，input 侧增长不会突破上下文窗口（当前模型 16k/32k 级）。建议：人物树控制在 10 角色内 + relations 精简单行，避免把 6000 字符 lore 顶到 8000+。

  【2. 字数不达标重试策略成本】
  现 pipeline：draft(4096)→refine(2048)→evaluate(512, multi-dim 时 N 维并行)→safety；pipeline_max_iters=3、score_threshold=0.75、_HARD_MAX_ITERS=5。
  - 整章重生：重新走 draft+每次 refine 迭代 ≈ **完整管线一次 ≈ 3000-5000 output token + 对应 input 重放**；且已有内容作废，TTFT 拉满，用户等待感强。
  - 续写补足（推荐：continue 分支仅 draft+safety，已存在且 _should_run_stage 支持）：在现有 80-90% 文本上追加 → 仅 **≈500-1000 output token + 短 input**，成本约为整章重生的 **15-25%**，且保留已有分章一致性。
  **建议阈值**：
  - 差距 ≤10%（字数 90%-110%）→ 直接接受，不重试（LLM 字数估算偏差本来就 ~10%）。
  - 差距 10%-40%（写少了）→ continue 续写补足 1 次，目标 = 剩余差额，成功即收尾。
  - 差距 >40% 或两次续写仍不足 → 才整章重生（白名单罕见路径）。
  - 字数超限 >20% 同理用 continue 续写反而无用，建议 refine 压缩或接受超限（成本低于重写）。
  - 避免把字数硬绑到 evaluate 分数：当前 evaluate 只评质量，绑字数会高频触 refresh→迭代成本翻倍，破坏 pipeline_max_iters=3 的成本上限。

  【3. embedding 缓存现状与放大风险】
  现状（app/llm/embedding.py）：内存 TTL 缓存，_EMBED_CACHE_TTL_SECONDS=3600、MAX_ENTRIES=4096、key=identity|model|sha256(text)；每次 pipeline retrieval 只 embed 1 次 query（topic）。
  - 本次改动**不会放大 embedding 调用**：注入的是 system prompt 静态上下文（人物树/前文/章节数），不改变 query 文本；同一 query 命中缓存。
  - 唯一风险：若把**人物关系树/章节数拼进 topic 文本**（retrieve 以 topic 为 query）→ 每次生成 query 都不同 → cache 全 miss → 每次网络 embed（100-500ms/次）+ 入 token 计费。**务必保持注入进 system 而非 query**。
  - 提醒：BYOK 时 cache identity=api_base+key sha256，不同租户不共享——多租户下 TTL 命中率天然低，属预期，不是本次改动引入。

  结论：kiro 方案可行，成本可控（+400-1400 input token/次）；字数不足优先 continue 续写补足（成本 15-25%），阈值如上；人物树/章节数必须放 system prompt，避免污染 retrieval query 使 embedding 缓存失效。
